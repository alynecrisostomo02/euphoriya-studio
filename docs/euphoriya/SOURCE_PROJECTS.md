# Source projects audit

**Scope:** source archives currently in this repository, inspected on 2026-10-02. The ZIPs do not provide reliable Git commit identifiers; versions below come from their manifests. The projects remain isolated at the repository root, `narra/`, and `loreum/`. This is an architectural audit, not a security or legal opinion.

## Current architecture

### Fantasia Archive — repository root

- **Application and shell:** Fantasia Archive 2.4.16, Quasar 2, Vue 3, TypeScript 6, and Electron 41. This is the current desktop shell, not yet the finished Euphoriya product.
- **Process boundaries:** the renderer owns Vue/Pinia UI state. A sandboxed Electron preload exposes allowlisted APIs through `contextBridge`; renderer requests travel over typed IPC to the Electron main process. Filesystem and SQLite access belong in main, not preload.
- **Persistence:** `better-sqlite3` opens one local `.faproject` SQLite file per project. Project files use `PRAGMA user_version` and have an implemented upgrade path through schema v11. `project_data` is a small key-value table for project preferences; core content is relational.
- **Existing project/content model:** `worlds`, `document_templates`, `documents`, `media`, `document_media`, world/template hierarchy and layout tables, tags and document-tag junctions, opened-document snapshots, and last-opened-document records. Document templates are shells: typed template custom fields are an approved design but are not implemented. A document may reference a template and its place in a world-specific hierarchy. Existing tables do not yet provide Euphoriya's universal entity, relationship, canon, or character-knowledge model.
- **Database access and migrations:** SQLite DDL and migrations live under `src-electron/mainScripts/projectManagement/`. Database work follows small main-process wiring modules and calls such as `runWithFaProjectDatabaseForIpcAsync`; the supported schema maximum is v11. Existing migrations run in transactions and existing open-time patches are designed to be idempotent. The current creation path sets `journal_mode = DELETE` and validates the created file with `quick_check`.
- **Models, templates, and custom fields:** domain interfaces are in `types/`; document templates have localized titles, world-specific placements, and a hierarchy. Custom fields are specified separately in `docs/database/templateCustomFields.md` as relational definitions plus typed values and stable field IDs, but remain unimplemented. This is useful prior art, not an already shipped capability.
- **Stores and UI:** Pinia stores under `src/stores/`, feature components/pages under `src/`, and route/layout code compose the desktop workspace. The current UI centers on worlds, document templates, a document hierarchy/workspace, tabs, project settings, and project overview.
- **Project lifecycle and media:** users create/open `.faproject` files via Electron dialogs; project management retains recent-project and active-database state. Media metadata is in SQLite and linked to documents using `document_media`. Existing media supports internal/external links and embeds; internal embedded bytes can be stored as a BLOB. Euphoriya should use managed files plus database references for large assets.
- **Import/export:** source includes project/content persistence, E2E staging, and project media/document paths; it does not provide the Euphoriya source-project adapters described in the convergence plan. A future import must use explicit adapters and preserve source files.
- **Tests:** Vitest covers renderer, Electron, helpers, and i18n; Playwright covers component/E2E behavior; Storybook is used for component and visual testing. SQLite schema, migration, and persistence tests use real in-memory `better-sqlite3` databases in addition to wiring tests.

### Narra — `narra/`

- **Application and architecture:** Narra 0.1.0 is a Rust 2021 CLI and stdio MCP server, organized as `CLI/MCP → AppContext → services → repositories → embedded SurrealDB/RocksDB`. Both entry points share injected service traits; tests can substitute providers and an embedding service.
- **Entities and storage:** its schema has separate SurrealDB records/tables for characters, locations, timeline events, scenes, relationships, knowledge, perceptions, facts, notes, phases, and annotations. It does not use one universal entity table. Relationship and participation data use graph edges; records and relationships are evolved through numbered `.surql` migrations.
- **Character psychology:** `Character.profile` is a flexible map from profile keys such as wound, desire, contradiction, and secret to lists of strings. This is useful feature inspiration; the map itself should not replace typed/core character identity or migrate directly as an opaque JSON profile.
- **Relationships and knowledge:** graph relationships connect characters with types/subtypes/labels. Knowledge records and per-character knowledge states distinguish certainty (including suspects and believes-wrongly) and learning provenance/methods. Perceptions are directional. Universe facts can apply to multiple entity kinds.
- **Narrative and graph:** events, scenes, participants, phases, and arc snapshots support narrative sequencing and analytics. Graph services cover pathfinding, neighborhood/proximity, influence, and graph analytics. Analytics also include irony, consistency, tension, themes, clustering, character arcs, and impact.
- **Search and AI:** keyword and hybrid/semantic search, embeddings (384-dimension BGE-small-en-v1.5) with a local offline backend, reranking, and embedding maintenance. The MCP server exposes tools, resources, and prompts. Its local model runtime and SurrealDB are not assumed necessary for the desktop MVP.
- **Tests and reuse:** Rust unit and integration tests, isolated database instances, builders, and CI Clippy/format/test checks. Narra is MIT licensed; an algorithm may be independently ported or selectively reused with its copyright/license notice, but no Narra implementation has been transplanted into Euphoriya.

### Loreum — `loreum/`

- **Application and architecture:** Loreum is a pnpm 12/Turborepo TypeScript monorepo. `apps/web` is Next.js 16 + React 19; `apps/api` is NestJS + Prisma. Shared types/UI and TypeScript/ESLint configuration live under `packages/`.
- **Persistence and services:** PostgreSQL 18 is the primary relational database. Prisma migrations define the schema. Redis 7 supports BullMQ jobs/queues and related operational services; the documented architecture also includes OpenSearch for full-text indexing. Cloudflare R2 is object storage. Running the stack requires service configuration and Docker Compose.
- **World model:** a project-scoped `Entity` base has a fixed enum of character/location/organization/item plus one-to-one specialized rows, with relationships, tags, and typed project-scoped custom item types. This is strong prior art for shared identity and queryable links; Euphoriya should use an extensible `EntityType` table rather than copy Loreum's fixed enum or its account/project assumptions.
- **Feature modules:** the API and UI include entities, entity types, relationship graph, eras/events/timeline, lore wiki articles, tags, maps/location pins, and storyboard plotlines, plot points, works, chapters, scenes, scene participants, and style guide. The README describes 36 MCP tools; web/API routes and Prisma are independently testable.
- **Search and AI:** full-text search, a remote Streamable HTTP MCP endpoint, OAuth 2.1/API-key authorization, and project-pinned reads/writes. AI-proposed-change review is described as roadmap work, not an already complete review queue. The desktop product should not add Loreum's web service, user accounts, or cloud authorization to its local data foundation.
- **Media and security boundary:** map/image media is stored in Cloudflare R2 with CDN-backed URLs; this assumes cloud infrastructure unlike offline-first Euphoriya. Loreum implements Google OAuth/JWT sessions, OAuth clients/tokens, per-project API keys, visibility/public wiki, and subscription models. These are web deployment/product capabilities, not requirements of the desktop MVP.
- **Tests and licensing:** API tests use Vitest/Supertest; CI and shared package type/lint tasks are documented. Loreum is AGPL-3.0 licensed; no Loreum implementation has been copied into Euphoriya's application code.

## Overlap and technical recommendations

1. **Shared entities and custom fields:** Loreum proves a common entity key is useful; Fantasia has world-scoped templates and a detailed planned relational field design; Narra demonstrates psychology keys. Use a normalized extensible entity registry and stable-ID custom fields, not three parallel entity registries, fixed per-product enums, or an unbounded profile JSON object.
2. **Relationships and graph:** Narra and Loreum both store typed relationships; Fantasia's hierarchy is a distinct parent/order structure, not a substitute. Store world relationships separately from hierarchy. Begin with indexed SQLite edges and TypeScript traversal. Bring in a graph runtime only if measured product needs justify it.
3. **Timeline and stories:** Narra and Loreum overlap on events/scenes; Loreum contributes works/chapters/plotlines and eras; Narra contributes knowledge at narrative time, phases, arcs, and analysis. Represent story/time once in relational Euphoriya tables; do not import either timeline wholesale.
4. **Knowledge versus world canon:** Narra's knowledge-state/provenance concepts are the strongest model for what a character knows; Loreum lore articles are closer to authored world-bible content. Keep canonical claims/evidence, authored wiki/story content, and each character's belief state separate.
5. **Storage and search:** Fantasia already ships local SQLite with migrations and native Electron binding. PostgreSQL/Redis/R2 fit Loreum's multi-user hosted service; SurrealDB/RocksDB and local embeddings fit Narra's Rust semantic engine. Those choices do not outweigh the requested offline, single-file desktop core. Start with SQLite/FTS5 and a filesystem media library.
6. **Auth, hosted operations, and semantic model runtime:** Loreum account billing/OAuth/cloud visibility and Narra Rust/SurrealDB/embedding runtime are not MVP dependencies. Reconsider cloud synchronization, external authentication, or an embedding sidecar only as separately scoped product requirements.

## Reuse and licensing status

Source trees are preserved in place with their project licenses and attributions. Imports into these source-project directories retain upstream paths; **no implementation code has yet been copied across project boundaries or into a new Euphoriya feature**. The planned database/domain design and the initial foundation module are original Euphoriya work.
